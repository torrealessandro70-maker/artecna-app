# F4C.1 — capability Desktop locale

Migration additiva dopo F3C3.7 → F3C3.1 → F3C3.2 → F3C3.3. Nessuna migration storica modificata. Nessuna scrittura dominio, tabella operativa, credenziale o URL permanente aggiunta.

`public.elenca_foto_rapportino_desktop(uuid)` è STABLE, SECURITY DEFINER, owner postgres, search_path fisso. Solo authenticated riceve EXECUTE. PostgREST verifica JWT e imposta ruolo/claims; SQL usa gli helper Desktop Production certificati. Deriva cantiere/data dal Rapportino, controlla membership owner e restituisce esclusivamente mapping Allegato/proiezione/Rapportino e MIME/peso. Il marker browser non basta ad autorizzare.

`artecna_foto_desktop.risolvi(uuid,uuid)` è riservato al LOGIN esistente artecna_rapportini_backend. Il secondo UUID è un'attestazione del backend fidato: il FUTURO endpoint deve ottenere l'utente tramite verifica autorevole JWT (es. Supabase Auth getUser), MAI accettare user_id/claims decodificati dal payload. Il resolver non verifica firme JWT autonomamente e non deve essere esposto tramite proxy generico. Il parametro è necessario perché il backend PostgreSQL Mobile non eredita le claims PostgREST Desktop. Ricontrolla membership e contesto, stato finalizzato, path canonico, reciprocità e marker; restituisce bucket/path/hash solo al backend. Nessun nuovo LOGIN/ENV. Service_role non riceve EXECUTE. Il helper verifica resta owner-only.

Il trust boundary include il backend autorizzato e l'amministratore: la capability non protegge da impersonazione da parte di un backend compromesso. Prima del completamento F4C è obbligatorio collegare la verifica JWT server, senza fallback Mobile, e l'adapter Storage autorizzato. UI/API/Storage non sono implementati in questo step.

Preflight: installer, ruoli, assenza degli oggetti, marker core, fingerprint CRLF→LF senza CR isolati dei tre helper certificati, owner/config/firma/tipi e ACL del resolver core. Postcheck preserva metadata/OID/ACL di tutte le funzioni esistenti, ACL/RLS/owner delle relazioni, ACL schemi e membership. Grant dei soli nuovi oggetti neutralizzati anche in presenza di default privileges. Ripetizione abort, nessun CREATE OR REPLACE legacy.

Test PostgreSQL 17.6 reale con sequenza sostitutiva, claims JWT emulati come contesto fidato PostgREST: non certificano verifica firma HTTP/JWT o Storage API. Le anomalie di marker/reciprocità sono iniettate SOLTANTO nella fixture con session_replication_role replica, ripristinato origin prima della lettura e rollback; nessuna guardia Production o file certificato alterato. Concorrenza segue MVCC: richieste iniziate prima del commit di revoca possono vedere la membership precedente; una nuova richiesta dopo commit viene negata. Non promette revoca retroattiva dei byte già consegnati.

Production resta NO-GO. La disponibilità dell'identità backend e degli helper va ricertificata prima dell'applicazione remota.
